# Componenta Skeleton

Стартовый проект для PHP 8.5.13+ с пресетами HTTP, CLI и WebSocket.

## Установка

```bash
composer create-project componenta/skeleton my-app
cd my-app
php bin/console.php list
```

Установщик выбирает зависимости, создаёт точки входа и локальный `.env`, затем удаляет свои установочные файлы. Без интерактивного ввода выбирается Web с Nyholm PSR-7, Plates, Pest, CQRS и политиками.

| Пресет | Возможности |
|---|---|
| Web | HTTP, маршрутизация и опциональные шаблоны |
| API | HTTP и маршрутизация, по умолчанию без шаблонов |
| Full | HTTP, шаблоны, CQRS, политики, аутентификация и Cycle ORM |
| CLI | Консольные команды |
| WebSocket | WebSocket-приложение |

HTTP-пресеты поддерживают Nyholm, Diactoros, Guzzle и Slim. Интерактивная установка позволяет выбрать Pest или PHPUnit и дополнительные интеграции. Full использует Nyholm, Plates и Pest. WebSocket можно добавить к другому пресету.

**На этой ветке проверены:** сгенерированные проекты Web, API и CLI. Для Full/Auth и WebSocket ещё нужен отдельный переход зависимостей/API; подробности — в [совместимости пресетов](docs/preset-compatibility.md).

## Конфигурация и жизненный цикл

Точки входа загружают Composer и вызывают `Componenta\App\run()` с областью выполнения и `PathResolver`. Приложение загружает `config/container.php`.

`config/config.php` возвращает `ConfigDefinition` с провайдерами, конфигурационными файлами и опциональными директориями дискаверинга. `Componenta\App\Config\ConfigFactory` подготавливает композицию из runtime Config и отдельных определений зависимостей. `Componenta\DI\ContainerFactory` получает эти объекты и создаёт контейнер. Фабрики получают `ContainerValue` и обращаются к тому же Config через `$container->config`.

Composer генерирует `config/componenta-providers.php` из метаданных пакетов. Провайдеры приложения можно помечать `#[AsConfig]` и размещать в `src/`; конфигурационные файлы находятся в `config/autoload/`.

Конфигурация собирается в каждом окружении. Настроенный источник классов передаётся через DI. Bootloader'ы подготавливают выбранную область выполнения.

## Сборка и развёртывание

Подготовка необязательна. Исходный режим остаётся полноценным способом запуска, в том числе в production. `APP_ENV` выбирает конфигурацию приложения, но не создаёт артефакты и не подтверждает наличие сборки.

~~~bash
composer install --no-dev --optimize-autoloader
APP_BUILD_ID="release-2026-11-27" php bin/console.php app:build
~~~

Задайте тот же `APP_BUILD_ID` при запуске приложения. Это идентификатор неизменяемого релиза кода и профиля структурной конфигурации: разным входным данным нужны разные идентификаторы. Если ID не задан, код и артефакты должны развёртываться вместе и пересобираться после структурных изменений. Runtime не вычисляет хеш всего дерева исходников и не запускает сборку автоматически.

Точка входа CLI вызывает `BuildConsole` сразу после autoload, до создания обычного контейнера и вызова bootloaders. В deployment используйте полные имена `app:build` и `app:clean`. Сборка составляет конфигурацию из текущих исходников в свежем контейнере: новый `#[AsConfig]` или удалённое объявление учитываются с первой пересборки, без предварительной очистки. Код провайдеров выполняется для определения сборки; целый объект Config и живые сервисы не сериализуются. Доменные артефакты могут включать структурную конфигурацию, например регистрации обработчиков; она входит в идентичность релиза/профиля.

Каждый участник реализует `ApplicationBuilderInterface::build(BuildContext $build): void`. App записывает результаты в новый каталог `var/cache/build/generations/<generation>/`, создаёт manifest и переключает `current.json` только после успеха всех билдеров. Ошибка сохраняет прежнее опубликованное поколение. Неподдерживаемая необязательная оптимизация явно помечается и использует исходный путь; ошибка компиляции прерывает сборку.

| Артефакт | Подготовленные данные | Что выполняется в runtime |
|---|---|---|
| `app.discovery` | Упорядоченные объявления классов | Загрузка нужных классов |
| `app.config-providers` | Упорядоченные имена классов `#[AsConfig]` | Создание и вызов провайдеров, составление конфигурации |
| `app.boot` | Принадлежность методов к boot | Создание атрибутов, DI-аргументы, вызовы методов |
| `console.commands` | Принадлежность классов к командам | Создание и регистрация команд |
| `router.routes` | Переносимая схема компилятора Router | Обработка запроса, DI, исходный путь для динамического контекста |
| `cqrs.maps` | Описания обработчиков и listeners, приоритеты | Dispatch и runtime callbacks |
| `validation.rules` | Поддержанные литеральные описания валидации | Новые экземпляры правил/валидаторов, fallback остальных DTO |

Подготовка схемы Cycle включается отдельно и явно в Cycle App: компилятор может читать метаданные БД, но сборка не должна синхронизировать таблицы или выполнять миграции. Interceptor 4 использует собственный runtime-кеш атрибутов и не требует build-карты; Skeleton больше не устанавливает избыточный Interceptor App.

Bootstrap закрепляет один `PreparedBuild`. Пересборка и очистка не переключают карты под уже работающим worker. При обновлении кода перезапускайте workers. `app:clean` снимает только текущий указатель, не вызывает провайдеры и сохраняет поколения для действующих процессов. Удаляйте старые каталоги поколений при очистке релизов после остановки этих процессов.

Отсутствующий или несовместимый необязательный артефакт использует исходный режим. Для обязательной подготовки передайте `requiredArtifacts` в `ApplicationBuildRunner::build()` и runtime `ConfigFactory::create()`, например `['app.discovery', 'app.config-providers', 'app.boot', 'console.commands']`. Пустой список билдеров и пустые карты корректны. Такая политика не зависит от `APP_ENV`.

### Переход с отдельных карт

Пользовательский билдер должен принимать `BuildContext`, заменять прямую запись файла на `$build->write('vendor.artifact', $payload, schemaVersion: 1)` и отмечать намеренно неподдерживаемую оптимизацию через `$build->skip('vendor.artifact', $reason)`. Неожиданные исключения должны выходить наружу. Зависимости исходных данных остаются в конструкторе. Билдеры не читают результаты других участников текущего запуска.

Индивидуальные cleaners, аргументы путей/поколений в конструкторах и независимые readers `classes.php`, `boot.php`, `commands.php` заменены общим протоколом. Старые файлы игнорируются; пересборка создаёт новое поколение. Наличие runtime-снимка проверяется через `AppConfigKey::PREPARED_BUILD`, а не через возможность autowiring его класса.

Ветка предназначена для App/Console 6, Config 4, DI 6, Router 4 / Router App 6, CQRS 5 / CQRS App 6, Validation 3.2 / Validation App 4, Error Handler App 2 и необязательного Cycle App 3 на PHP 8.5.13+. Root manifest и installer содержат ограничения релизных версий. Перед публикацией этого Skeleton соответствующие релизы должны быть доступны вместе; разработка проверяется отдельным integration-проектом с явно выбранными ветками.

## Разработка

- `composer test` проверяет настоящий bootstrap и справку команды сборки.
- `composer serve` запускает HTTP-сервер для разработки.
- `bin/console.php` — точка входа консоли.
- HTTP-пресеты добавляют `public/index.php`, конфигурацию маршрутов и middleware.
- WebSocket-пресеты добавляют `bin/websocket.php` и `config/websocket.php`.

Подробности находятся в документации [App](https://github.com/Componenta/app), [DI](https://github.com/Componenta/di), [Config](https://github.com/Componenta/config), [Router App](https://github.com/Componenta/router-app), [CQRS App](https://github.com/Componenta/cqrs-app), [Interceptor](https://github.com/Componenta/interceptor), [Validation App](https://github.com/Componenta/validation-app), [Policy](https://github.com/Componenta/policy), [Cycle App](https://github.com/Componenta/cycle-app) и [WebSocket App](https://github.com/Componenta/websocket-app).
